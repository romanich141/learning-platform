# Streaming Gallery — як усе працює разом

Повний прогін по проєкту: від HTTP-запиту в браузері до інтерактивної кнопки ❤️.
Це підсумок усього, що ми вивчили про `renderToPipeableStream`, крок за кроком.

## Головна ідея: `App` — це ОДНЕ дерево компонентів, яке виконується ДВІЧІ

Це найважливіше, що варто зрозуміти. У проєкті не два різні додатки — це **той самий код**
(`App` → `Gallery` → `Album` → `LikeButton`), який запускається у **двох абсолютно різних середовищах**:

```
                    app/App.tsx (той самий файл!)
                   /                            \
                  /                              \
    server/server.tsx                      client/client.tsx
    (Node.js, немає DOM)                   (браузер, є DOM)
         │                                       │
  renderToPipeableStream                   hydrateRoot(document, ...)
  → генерує HTML-РЯДКИ                    → не малює заново, а
    (текст, який летить                     "підв'язує" React до
     по мережі)                             вже існуючого DOM
```

**Навіщо так:** сервер швидко віддає готовий HTML (добре для швидкого першого показу й SEO),
а клієнт бере той самий HTML і **оживляє** його (додає обробники подій, `useState` тощо),
не перемальовуючи з нуля. Якби клієнт **перемалював** дерево (як звичайний CSR-рендер),
сенс SSR-стрімінгу зник би — довелося б чекати весь JS-бандл і рендер заново.

## Ключова умова: обидва запуски мають отримати ОДНАКОВІ пропси

Ось чому в проєкті є ціла механіка з `query`:

1. **Сервер** (`server.tsx`) парсить `req.url` → `query = Object.fromEntries(url.searchParams)`.
   Це звичайний об'єкт `{a: "1000", b: "3000", mode: "shell"}`.
2. Цей `query` іде в `<App query={query} />` → рендериться в HTML із конкретними `delay`
   для кожного альбому.
3. Щоб клієнт (`client.tsx`) міг відрендерити **те саме дерево з тими самими пропсами**,
   йому теж потрібен цей `query` — але в браузері немає `req.url`! Тому сервер **вбудовує**
   query прямо в HTML:
   ```ts
   bootstrapScriptContent: `window.__QUERY__ = ${JSON.stringify(query)};`,
   ```
4. Клієнт читає це з `window.__QUERY__` і викликає
   `hydrateRoot(document, <App query={window.__QUERY__} />)` — **той самий** `query`,
   що бачив сервер.

Якби query відрізнялися (наприклад, сервер порахував `delay=1000`, а клієнт — `delay=2000`) —
React побачив би **hydration mismatch**: HTML, який він очікує згенерувати сам, не збігається
з тим, що вже намальовано сервером. React про це попередить у консолі й перемалює розбіжність.

## Повний цикл одного запиту — крок за кроком

### 1. Браузер робить `GET /?a=1000&b=3000&c=500`

### 2. `server.tsx` приймає запит

```ts
const query = Object.fromEntries(url.searchParams);   // {a:"1000", b:"3000", c:"500"}
const mode = query.mode === "all" ? "all" : "shell";
resetCache();   // ← ОБОВ'ЯЗКОВО перед рендером: чистий кеш для НОВОГО запиту
```

Кеш ресурсів (`resetCache()`) очищається **рівно раз на HTTP-запит**, до старту рендеру.
(Раніше він викликався всередині компонента `Album` на кожному рендері — це спричиняло
нескінченний Suspense: другий рендер після резолву промісу стирав сам себе і створював
новий `pending`-ресурс. Див. розділ "Побічні уроки" нижче.)

### 3. Стартує `renderToPipeableStream(<App query={query}/>, {...})`

React починає рендерити дерево **синхронно**, зверху вниз:

- `App` → `head`, `body`, `header` — усе це **шелл** (усе поза `<Suspense>`), рендериться миттєво.
- `Gallery` мапить `ALBUMS`, для кожного рахує
  `delay = getAlbumDelay(album.delayKey, query)` — тут `parseInt` перетворює рядок `"1000"`
  на число, бо query-параметри завжди рядки.
- Кожен альбом обгорнутий у `<Suspense fallback={...}>`.
- Усередині — `<Album id={...} delay={...}>`. У ньому:
  ```ts
  const album = getAlbum(id, delay).read();
  ```
  `getAlbum` бере ресурс із кешу або створює новий (`fetchAlbum`). `.read()`:
  - якщо `pending` → **кидає проміс** → React ловить це, показує `fallback` цього
    конкретного `<Suspense>`, і йде рендерити далі (наступний альбом), **не блокуючись**;
  - якщо `success` → повертає дані → рендериться реальний контент.

### 4. Коли всі "спроби" рендеру зроблено — спрацьовує `onShellReady()`

```ts
if (mode === "shell") {
  res.write("<!DOCTYPE html>");
  pipe(res);   // ← СТАРТ стріму
}
```

Тут `pipe(res)` починає писати HTML у `res` (Node `Writable`) — браузер отримує перші байти.
**З'єднання лишається відкритим.**

### 5. У міру того, як проміси кожного альбому резолвляться

(через `setTimeout` у `sleep`), React **повторно рендерить** саме той `Album`, `.read()`
тепер повертає дані замість кидання промісу — і React **доливає** новий chunk у той самий
відкритий `res`: HTML контенту + `<script>$RC(...)</script>`, який на клієнті підміняє
fallback на реальний контент у DOM.

### 6. Коли резолвились геть усі — `onAllReady()`

У `mode=shell` цей колбек нічого не пише (уже все відправлено через `onShellReady`+доливання).
У `mode=all` — саме тут вперше пишеться `pipe(res)`, тобто вся відповідь іде одним шматком,
без часткового стріму (поведінка, еквівалентна `renderToString`).

### 7. У згенерованому HTML сервер (через опції, а не JSX) вставив

```html
<script id="_R_">window.__QUERY__ = {...};</script>
<script src="/client.js" async></script>
```

### 8. Браузер, отримавши HTML, парсить його й одразу бачить `<script src="/client.js">`

→ робить `GET /client.js`. Цей запит ловить окрема гілка на самому початку `server.tsx`:

```ts
if (url.pathname === "/client.js") {
  fs.createReadStream("public/client.js").pipe(res);   // просто роздача статичного файлу
  return;
}
```

`public/client.js` — це **зібраний esbuild-ом** `client/client.tsx` (командою
`npm run build:client`). Сервер сам ніколи не імпортує `client.tsx` — це геть окремий
білд-артефакт.

### 9. Браузер виконує отриманий `client.js`

```ts
hydrateRoot(document, <App query={window.__QUERY__} />);
```

React проходить по вже намальованому DOM і **підв'язує** обробники (`onClick` у
`LikeButton`, `useState` тощо) до існуючих вузлів — не перемальовуючи їх заново.

### 10. Кожен `<Suspense>`-боундарі гідрується незалежно

У міру появи в DOM — саме тому клік по ❤️ на альбомі, що доліввся через 5 секунд, спрацював:
React встиг гідрувати саме цей шматок, коли його контент з'явився, окремо від решти дерева.

## Побічні уроки, які ми здобули по дорозі

| Що | Урок |
|---|---|
| Баг з `resetCache()` у компоненті | Кеш ресурсу мусить жити **між** двома рендерами одного компонента (suspend → retry), а очищатись — **раз на HTTP-запит**, не частіше |
| `mode=shell` vs `mode=all` | `renderToPipeableStream` сам по собі не «стрімить» — стрімінг це твій вибір, **де** викликати `pipe(res)` |
| CPU-throttle експеримент | Гідрація — звичайний синхронний JS; поки він виконується, події (клік) чекають у черзі — фундаментальне обмеження JS, не магія React |
| `?a=&b=&c=` затримки | Query-параметри — це просто **рядки**, завжди потрібен `Number`/`parseInt`; кожен `<Suspense>` резолвиться незалежно, у порядку готовності даних, а не порядку в дереві |

## Три ключові колбеки `renderToPipeableStream`

| Колбек | Коли | Що робимо |
|---|---|---|
| `onShellReady` | шелл готовий (найраніше) | `pipe(res)` — стартує стрім |
| `onShellError` | фатальна помилка ДО шелла | 500 + запасний HTML |
| `onError` | будь-яка помилка (шелл або боундарі) | лог + прапорець статусу |

`onShellReady` і `onShellError` — взаємовиключні (спрацює рівно один). `onError` спрацьовує
в обох випадках як логер.
