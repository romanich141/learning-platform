# Шпаргалка: curl-команди для дослідження стрімінгу

Довідка по `curl`-командах, якими ми перевіряли поведінку `renderToPipeableStream`.
Для кожної — що робить, які прапорці означають і що дивитись у результаті.

---

## Довідка по прапорцях curl

| Прапорець | Що робить |
|---|---|
| `-N` (`--no-buffer`) | Вимикає буферизацію виводу curl — ти бачиш байти в терміналі в міру надходження, а не одним шматком у кінці. **Головний інструмент** для спостереження за стрімінгом. |
| `-s` (`--silent`) | Не показувати прогрес-бар curl. |
| `-o <file>` / `-o /dev/null` | Куди зберегти тіло відповіді (`/dev/null` — якщо цікавить лише тайминг, не вміст). |
| `-w "<формат>"` | Вивести додаткові метрики після завершення запиту (тайминги, код статусу). |
| `--max-time <сек>` | Обірвати запит, якщо він не завершився за N секунд. Корисно, щоб зловити «зависання» (нескінченний suspend), а не чекати вручну. |

---

## 1. Базова перевірка, що сервер відповідає

```bash
curl -s -o /dev/null -w "HTTP %{http_code}\n" "http://localhost:3000/"
```
**Навіщо:** швидко перевірити, що сервер живий і повертає `200`, не завантажуючи й не показуючи HTML.

---

## 2. Побачити стрімінг наживо (`-N`)

```bash
curl -N "http://localhost:3000/"
```
**Навіщо:** головний інструмент усього проєкту. Без `-N` curl чекає **повну** відповідь і показує все одразу — ти не побачиш різниці між "шелл прилетів одразу" і "контент доливається пізніше". З `-N` бачиш у терміналі в реальному часі: спершу HTML шелла+скелетонів, потім — паузу, потім чергові шматки HTML для кожного альбому, у міру того як `<Suspense>` резолвиться.

**Приклад для M2 (коли `delay` буде в query):**
```bash
curl -N "http://localhost:3000/?delay=2500"
```
Очікувано: скелетон з'являється миттєво, через ~2.5с у терміналі "дописується" HTML альбому.

**Приклад для M4 (кілька альбомів з різними затримками):**
```bash
curl -N "http://localhost:3000/?a=1000&b=3000&c=500&d=2000"
```
Очікувано: альбоми доливаються **не по порядку в дереві**, а в порядку готовності — той, що з `delay=500` (найшвидший), з'явиться першим.

---

## 3. Ловимо баг «нескінченний suspend» (`--max-time`)

Використовували, коли `resetCache()` викликався всередині `Album` і стирав кеш сам собі — альбоми ніколи не резолвились.

```bash
curl -s --max-time 12 -o /tmp/resp.html -w "HTTP %{http_code}, час: %{time_total}s\n" "http://localhost:3000/"
```
**Навіщо:** без `--max-time` такий запит просто «висів би» вічно, і незрозуміло — це повільно чи зламано. З лімітом curl сам обірве з'єднання через 12с, і ми бачимо `time_total` ≈ 12.00s — ознака, що відповідь **так і не прийшла повністю** (порівняй із очікуваним часом найповільнішого альбому).

**Що дивитись у результаті:**
```bash
grep -c "Назва_альбому" /tmp/resp.html   # 0 = альбом так і не долетів
```

## 4. Порівняння `mode=shell` vs `mode=all` (M3): TTFB

```bash
curl -s -o /dev/null -w "TTFB: %{time_starttransfer}s, повний час: %{time_total}s\n" "http://localhost:3000/?mode=shell"
curl -s -o /dev/null -w "TTFB: %{time_starttransfer}s, повний час: %{time_total}s\n" "http://localhost:3000/?mode=all"
```
**Навіщо:** `%{time_starttransfer}` — це TTFB (Time To First Byte), момент, коли прийшов **перший** байт відповіді. `%{time_total}` — коли відповідь **повністю** завершилась.

**Що дивитись:**
- `mode=shell` (пишемо в `onShellReady`): TTFB **маленький** (~0.01s) — шелл летить одразу, а `time_total` дорівнює часу найповільнішого альбому (бо з'єднання тримається відкритим, поки все не доллється).
- `mode=all` (пишемо в `onAllReady`): TTFB **дорівнює** `time_total` — увесь HTML прийшов одним пакетом лише тоді, коли геть усе було готово. Це поведінка, еквівалентна `renderToString`.

**Наш реальний результат при перевірці:**
```
mode=shell:  TTFB 0.008s  →  повний час 5.01s
mode=all:    TTFB 5.01s   →  повний час 5.01s   (TTFB == повний час!)
```

## 5. (План на M6) Помилки та обрив рендеру

```bash
# Один альбом падає навмисно — решта галереї має лишитись живою
curl -N "http://localhost:3000/?failAlbum=nature"

# Фатальна помилка ДО шелла — очікуємо 500 і запасний HTML
curl -N "http://localhost:3000/?failShell=1"

# Обрив рендеру через 1с (abort()), поки альбом ще вантажиться 5с
curl -N "http://localhost:3000/?abortAfter=1000&delay=5000"
```
**Навіщо:** перевірити різницю між "впав один боундарі" (сторінка жива, `onError` спрацював) і "впав шелл" (`onShellError`, сторінки нема). `abortAfter` перевіряє, що `abort()` коректно обриває недописані частини потоку.

---

## Порада: якщо curl показує все одним шматком, хоча очікував стрім

Причини (за спаданням імовірності):
1. Забув прапорець `-N`.
2. Кеш ресурсу (`resetCache`) не викликається на новий запит — дані вже готові з попереднього разу, тож Suspense не встигає навіть спрацювати (усе миттєво).
3. Пишеш `pipe(res)` у `onAllReady`, а не в `onShellReady` (це і є `mode=all` — так і має бути одним шматком).
